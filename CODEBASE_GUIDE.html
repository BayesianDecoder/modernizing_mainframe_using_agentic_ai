How MAIA Live actually works

MAIA is a demo of one idea: instead of writing bespoke backend logic for every question a user might ask about a mainframe estate, give an LLM the shape of three data stores (~300 tokens) and let it write its own queries against them through the Model Context Protocol. Everything else in the repo — the simulator, the alert engine, the parser — exists to make that one idea demonstrable against something that looks like a real, live mainframe.

01 Problem 1 — The Invisible Cost (Billing Spikes)

Why the same batch schedule can cost wildly different amounts month to month — and why nobody notices until the invoice arrives.

R4HA, in plain English

IBM doesn't bill mainframe usage by adding up every second of CPU time used all month. It bills on the peak: every hour, it calculates the average MSU (Million Service Units — IBM's usage measure) consumption over the trailing 4 hours. Whatever the single highest one of those rolling 4-hour averages was, anywhere in the month, becomes the number your entire month's software licensing cost is based on. One bad night — two jobs accidentally overlapping for an hour — can permanently set the bill for every day in that month, even the 29 quiet days on either side of it.

Why crossing a tier threshold is so expensive

IBM's software pricing is tiered against that peak R4HA number — cross a threshold and the rate applies to the whole month's usage, not just the portion above it. Illustrative shape (real contract numbers vary):

Peak R4HA tierEffective rateWhat crossing it means
Up to 8,000 MSUBaseline rateNormal month
8,000–10,000 MSUNext tier upA single sustained hour of overlap can trigger this
10,000+ MSUHigher tier againThe exact boundary this project's simulator models (see the sample data's tier_boundary: 10000)

The mechanism that makes this dangerous: the tier is set by your peak hour, applied retroactively to the whole month. A scheduling accident on one Tuesday night is indistinguishable, on the invoice, from having run that hard all month.

Why this is usually a cross-team problem, not a within-team one

A real mainframe estate is rarely run by one team. Different business units own different applications — a payroll team, a billing team, an operations/reporting team — but they all run on the same shared hardware, sliced into LPARs. Two things make that combination dangerous specifically for R4HA:

  • Team visibility is siloed, but the bill isn't. R4HA is typically calculated across the whole machine complex, not per team. The payroll team has no visibility into when the billing team's batch window runs, and vice versa — so no single team individually "owns" the risk of their combined peak crossing a tier boundary, even though every team's own scheduling choices contributed to it.
  • LPARs get scheduled independently of each other. Even when each team nominally has its own LPAR, jobs still get scheduled without cross-team coordination — two unrelated teams' batch windows can drift into overlapping at the same time purely by coincidence, with neither team ever being told.

This project's own sample estate models exactly that: PAYJOB is owned by PAYROLL-TEAM, BILLJOB by BILLING-TEAM, NIGHTLY by OPS-TEAM (see the OWNER: field in each JCL file's header comment, The sample data) — three separate teams sharing one estate. Two things in the actual codebase exist specifically to catch this blind spot: alerts.py's rule_lpar_contention (detects two jobs on the same LPAR regardless of which team owns either one), and NIGHTLY.JCL's own documented issue — when BILLJOB (billing team) runs late, NIGHTLY (ops team) runs late too, one team's schedule slip silently becoming another team's SLA miss. A single graph spanning every team's jobs — not just one team's own view — is the only way to see that at all; no individual team's own tooling ever would, because no individual team's tooling looks past its own jobs.

The MAIA solution — and an honest note on what's actually built

Built vs. pitch

A dedicated "Cost Intelligence Agent" that scans for R4HA risk and produces a scored, proactive cost report is part of this project's original roadmap (its own CLAUDE_CODE_PROMPT.md "Priority 2" section) — it is not built. What genuinely exists and runs today: alerts.py's rule_rha_spike() (see alerts.py, line by line) computes a real rolling average from live SQLite data every 30 seconds and fires the moment it crosses 9,000 MSU — the actual, working half of this pitch, not the aspirational reporting layer on top of it.

The concrete number this pitch is built around comes straight from the sample data's own worked example (data/smf/sample_records.json): a rolling 4-hour average of 12,050 MSU against a 10,000 MSU tier boundary, driven by BILLJOB and CICS contention overlapping at quarter-end — "estimated_cost_impact": "$340,000 annually if this pattern repeats monthly". The fix isn't exotic: move the job start time by 30 minutes so it no longer overlaps the contention window (exactly what INCIDENT-002's own "Permanent Recommendation" prescribes) — a $0 scheduling change avoiding a $340,000 recurring cost, precisely because R4HA billing is unforgiving about when load happens, not just how much of it there is.

02 Problem 2 — Knowledge That Cannot Be Found

Three different kinds of knowledge disappear in three different ways — and a graph database only saves you from one of them.

The three types of mainframe knowledge

TypeWhat it isWhat happens when it's lost
StructuralWhat calls what, what reads what, what depends on what — facts that are technically in the source code, just not visible without reading every file Nobody can answer "what breaks if I change this" without a multi-day manual trace through source
OperationalHow things actually behave in production — typical runtimes, typical load, historical failure patternsNobody can tell a routine slowdown from a genuine emergency, because nobody remembers what "normal" looks like
TribalThe unwritten judgment an experienced engineer built up over years — "this always happens at quarter-end," "don't touch that on a Friday" Gone the day that person leaves. Never written down anywhere, so there's nothing left to search

Three real scenarios

1

An engineer paged at 3 AM

BILLJOB just failed with RC=8. Is this the well-understood CICS contention issue with a known 5-minute fix, or something new? Without the runbook, the on-call engineer has to reason from scratch, at 3 AM, under pressure.

2

A compliance request

An auditor asks: "show me every program that touches customer credit data, and prove each one enforces the RBI validation rule." That's exactly CREDITVAL's ADR-002 — answering it by hand means manually re-deriving the call graph the codebase already implicitly encodes.

3

A new engineer's first week

"What does BILLING actually do, and what shouldn't I touch?" Today that's a week of shadowing senior staff. The facts exist — in source code, in institutional memory — just not anywhere a newcomer can query them directly.

Why this isn't hypothetical — TSB Bank, 2018

TSB Bank's 2018 IT migration — moving customers off a legacy platform onto a new system without a complete, verified picture of every dependency — caused weeks of outages affecting millions of customers. The UK's Financial Conduct Authority and Prudential Regulation Authority later fined TSB and its parent Sabadell a combined £48.65 million (announced December 2022), specifically citing the bank's failure to adequately understand and test the system's real dependencies before cutting over. This is public regulatory record, not a hypothetical — the exact failure mode this problem describes, at a scale that made UK national news for weeks.

What MAIA actually does about it — this part is real

Structural knowledge → Neo4j, built by parser.py actually reading the COBOL/JCL source. Tribal knowledge → ChromaDB, holding the runbook's incident post-mortems — including, deliberately, Ramesh Kumar's own note about the quarter-end pattern, captured in writing specifically because he was retiring. Both are genuinely queryable today, by the chat feature writing real Cypher/semantic search against them — this is the one problem in this pitch whose entire proposed solution is fully built and running, not aspirational.

03 Problem 3 — Modernisation Without a Map

74% of mainframe migrations fail or overrun — almost always for the same reason: nobody had the dependency map before they started cutting code.

Why so many migrations fail

A migration project typically starts by picking a program to modernize, then discovers mid-project that three other programs call it, one of them is under regulatory audit requirements, and the "simple rewrite" just became a compliance incident. The failure isn't technical skill — it's sequencing a migration without first knowing the true shape of what depends on what.

Why COBOL specifically is harder than modernizing other legacy systems

COBOL's own structure resists exactly the kind of static analysis modern languages make easy: fixed-column source formatting from the punch-card era, GO TO-based control flow in older programs, external subroutine calls resolved only at runtime rather than through an explicit import system, and — the specific problem this project had to solve directly — a near-total absence of modern tooling (no bundled tree-sitter grammar, no mature language server) compared to essentially any language built in the last 20 years. Understanding a COBOL estate's true shape requires building tooling most other migrations can just download.

The four modernisation strategies

StrategyWhat it meansWhen it fits
RetireDecommission outrightNothing meaningful still depends on it — verifiable only with a real call graph, never by inspection alone
Rehost"Lift and shift" — same code, new infrastructure Low risk, buys time, doesn't reduce long-term maintenance burden
RefactorRestructure incrementally, preserving external behavior High-value shared modules with many callers, where a rewrite's blast radius is too large to risk outright
ReplaceRewrite entirely in a modern stack Isolated, well-understood, low-complexity modules — ironically the ones a graph shows as safest, not the ones that feel most urgent

Why sequence matters

Concretely, in this project's own sample estate: TAXCALC is a leaf module — a low complexity score, no outgoing calls, two known callers — a safe, early Refactor or Replace candidate. CREDITVAL has the same shape (a leaf, no outgoing calls) but carries an explicit regulatory constraint (ADR-002: a 30-day parallel run and Risk & Compliance sign-off required for any change) — touching it first, or without accounting for that constraint, is exactly the TSB-shaped mistake from Problem 2. The right sequence isn't "easiest first" or "most valuable first" — it's "known-safe-by-the-graph first," which requires having the graph before you start, not after.

Built vs. pitch

A "Modernisation Agent" that automatically scores every program by complexity and graph position and produces a sequenced roadmap is, again, part of the original roadmap and not built. What's real: parser.py's _score() already computes a genuine 0–10 complexity number per program today, and Neo4j already has the full call graph needed to compute "how many things depend on this" for any program, right now, with a single Cypher query. The scoring inputs exist; the agent that turns them into an automatic, sequenced roadmap does not — yet.

04 Problem 4 — Operational Blindness

Six questions a mainframe operations team is asked constantly, and can answer for maybe half of them today.

QuestionWhy it's hard today
Is any LPAR close to capacity right now?Requires actively watching a dashboard, not being told
Did any job fail in the last 30 minutes, and why?Requires someone to notice, then dig through logs by hand
Are two critical jobs about to collide on the same LPAR?Requires manually cross-referencing every job's schedule against every other's
Is tonight's batch about to push us into a higher billing tier?Requires computing a rolling average by hand, continuously — nobody does this live

Reactive vs. proactive operations

Reactive means finding out something's wrong because it already broke — a job already failed, an LPAR already hit 99% CPU. Proactive means knowing before it happens — predicting that tonight's batch overlap will breach SLA an hour from now, before a single job has actually run late. Five of the six questions above are reactive-but-automatic — genuinely useful, genuinely built — the sixth (true prediction) remains an open gap, honestly, not a solved problem.

MAIA's five alert rules — real, running, zero LLM cost

Full clause-by-clause SQL/Cypher for every one of these: alerts.py, line by line. In one line each: LPAR CPU > 85%, a job failed in the last 30 minutes, rolling MIPS average over the R4HA tier boundary, a job running >150% of its own historical average, two jobs sharing an LPAR.

The six-layer pitch, and which four layers actually got built.

The project's own design doc describes six layers, the last two of which were deliberately never built: automating changes back onto a mainframe is a compliance non-starter in any real bank or insurer, so the system stops at "produce a grounded recommendation" and a human takes it from there.

Two request paths run through this stack, on completely different budgets:

07 The sample data — in plain language

Everything under data/ is fiction, but it's one consistent fiction — the same facts repeated across three file types on purpose.

Before touching any code: data/ is a made-up bank's mainframe — 6 small COBOL programs, 3 batch jobs that run them on a schedule, and a runbook describing things that supposedly went wrong. None of it is real. But it was all written by one author telling one story, so the same fact — a name, a date, a dollar number — shows up in two or three different files. That's deliberate: it's what lets the chat feature find a real, specific, cross-checkable answer instead of a vague one.

What's an ADR?

Architecture Decision Record

A short note engineers write down whenever they make an important design choice, so that a year later — after the original author has left, or just forgotten — someone else can understand why the code is shaped the way it is, not just what it does. A good ADR has three parts: the decision ("we will do X"), the context ("here's the problem that made us choose X"), and the consequences ("here's what this means going forward, and what NOT to do"). RUNBOOK.md has two of them — ADR-001 and ADR-002 — and both are treated as still-active rules, not historical trivia.

Think of these less like "programs" and more like six little offices in a bank, each with one job, that sometimes call each other on the phone (CALL 'OTHER-PROGRAM') to get something done.

The runbook — three real-sounding stories

This is the file that gets loaded into ChromaDB, so it's worth knowing what's actually in it, in plain terms:

  • INCIDENT-001 — PAYJOB once ran out of disk space partway through (at employee record #47,832) because whoever wrote the JCL didn't leave enough room for the company to grow. Fixed by allocating more space.
  • INCIDENT-002 — the big recurring one. Every quarter-end, an unrelated online system (CICS) is still busy posting old charges when BILLJOB tries to start, so BILLJOB can't get at its data and fails for hours. There's a quick fix (cancel the stuck task) and an obvious permanent fix (just start BILLJOB half an hour later on quarter-end months) that a named engineer, Ramesh, kept asking to have approved before he retired.
  • INCIDENT-003 — LPAR-3 (the computer NIGHTLY runs on) once nearly maxed out its CPU because someone scheduled an unrelated cleanup job at the same time as NIGHTLY. Fixed by moving that cleanup job to an earlier, quieter time.
  • 3 SOPs (Standard Operating Procedures) — literal step-by-step instructions an on-call engineer follows for each of the above, e.g. exactly which command cancels the stuck CICS task.

The one file nothing actually uses

data/smf/sample_records.json is just documentation — it shows what a real mainframe's raw performance/job data looks like before anyone parses it (the file says so itself, in its own _comment field). No code in this repo reads it; simulator.py makes up its own simpler version of the same idea instead.

Why write it this carefully

Because the whole app's chat feature depends on there being a real, specific, checkable answer waiting to be found — not a vague one the model has to invent. Ask "why does BILLJOB keep failing?" and the honest answer requires the JCL's schedule, the runbook's root cause, and the exact error text to all agree with each other. If the sample data were sloppy or contradictory, every chat answer would feel made up, even when it wasn't.

08 Concepts primer — the technologies, from scratch

Everything from here on assumes these ideas. Read this once; every later section leans on it. Neo4j, ChromaDB, and tree-sitter each get their own full section later — this primer covers the ones that don't: how a browser talks to a server at all, what "async" actually means, and what LangChain/MCP/agentic AI are.

HTTP, REST, and what a "request" actually is

Every time a web page shows you data, somewhere a small text conversation happened over the network. The browser sent a request — a plain-text message like:

a real HTTP request, in full
GET /api/alerts HTTP/1.1
Host: localhost:8000
Accept: application/json

and the server sent back a response:

the response
HTTP/1.1 200 OK
Content-Type: application/json

{"alerts": [], "count": 0, "critical": 0, "high": 0}

REST is just a naming convention for organizing these requests: a URL names a resource ("alerts"), and the method (GET, POST) says what you want to do to it — GET means "give me data, change nothing"; POST means "here's data, do something with it (create, trigger an action)." GET /api/alerts reads the current alerts; POST /api/chat sends a question and expects Gemini to act on it. The body of a POST is usually JSON — plain text formatted as nested {"key": value} pairs, the universal format both Python and JavaScript can read and write natively.

FastAPI — turning Python functions into URLs

FastAPI is a Python library that listens for HTTP requests and routes each one to a plain Python function you wrote. The mechanism is a decorator — the @app.get(...) line sitting directly above a function:

the whole idea of FastAPI in 4 lines
@app.get("/api/alerts")
def get_alerts():
    return {"alerts": [], "count": 0}

Nothing calls get_alerts() directly anywhere in the code — the decorator registers it with FastAPI, and FastAPI calls it automatically whenever a GET /api/alerts request arrives, then converts whatever Python dict/list you return into a JSON HTTP response automatically. That's the entire trick: FastAPI is a big dictionary from "method + URL" to "which function to run."

async / await — one chef, many orders, never standing still

Normal ("synchronous") Python runs one line at a time — if a line takes 3 seconds (e.g. waiting on a network reply), the entire program is frozen for those 3 seconds. That's disastrous for a server handling many users at once. Async is a different execution model: a single thread that, instead of blocking on a slow operation, pauses that one task and goes to do other waiting work, coming back to the paused task the instant its result is ready.

The restaurant analogy

A synchronous chef takes one order, stands at the oven doing nothing else until it's done, then takes the next order. An async chef takes an order, puts it in the oven, and immediately takes the next order while the first bakes — checking back on each oven the instant a timer dings. One chef, many simultaneous orders in progress, nobody idle. That's async def and await: async def marks a function as "can be paused"; await is the pause point — "start this slow thing, and let other code run until it's ready."

This project needs it specifically because both a Gemini API call and an MCP tool call are slow network round-trips (seconds, sometimes over a minute) — async def chat(...) in claude_brain.py and every FastAPI endpoint that touches it are async so the whole server can keep answering other requests (like /api/alerts) while one slow chat request is still in flight.

Pydantic — a bouncer for incoming JSON

A raw HTTP request body is just untyped text. Pydantic lets you declare the shape you expect as a Python class, and FastAPI automatically checks every incoming request against it before your function ever runs:

backend/main.py
class ChatRequest(BaseModel):
    message: str
    history: list[dict] = []

If a request arrives missing message, or with message as a number instead of text, FastAPI rejects it automatically with a clear error — the endpoint function's own code never has to check "did the caller actually send what I need?" by hand.

CORS — one paragraph now, the full story later

Browsers refuse, by default, to let JavaScript running on one website read a response from a different website — even if that response is perfectly valid. CORS is the mechanism a server uses to explicitly say "these other origins are allowed to read my responses." This project's frontend (port 5173) and backend (port 8000) are technically different origins, so main.py configures this explicitly. There's a full section below (CORS, from scratch) with the security reasoning and a banking-site example — worth reading in full, since it trips up almost everyone new to web development.

LangChain, MCP, and "agentic AI" — teaching the vocabulary before the code

Agentic AI is the general idea behind this whole project's chat feature: instead of an LLM just generating text, it's given a set of tools (actions it can request) and allowed to decide, on its own, which ones to call and in what order, to answer a question it couldn't answer from training data alone — like "what's LPAR-3's CPU right now?", which requires actually looking, not guessing.

Tool calling is the specific mechanism: the model is shown a list of tools (each with a name, a description, and the shape of arguments it accepts), and instead of only replying with text, it can reply with "call tool sqlite_query with argument {"sql": "SELECT ..."}." Your code actually runs that, feeds the result back to the model, and the model continues reasoning — possibly calling more tools — until it has enough to answer in plain text.

MCP (Model Context Protocol) is a standard, vendor-neutral way to expose tools like this over a network, so any MCP-speaking model client can discover and call them without either side hard-coding the other. This project's mcp_servers/ folder runs 3 tiny MCP servers, each wrapping one database.

LangChain is a Python library that provides common building blocks — a ChatGoogleGenerativeAI class that talks to Gemini, message types (SystemMessage, HumanMessage, etc.), and langchain-mcp-adapters, which connects to MCP servers and converts their tools into the shape LangChain's chat models expect. It's the glue between "a model" and "a set of MCP tools" — fully explained in The brain below, with the actual tool-calling loop walked line by line.

09 The three knowledge stores

One estate, three different questions, three different databases — on purpose.

A recurring interview question worth having a crisp answer to: why three databases instead of one? Because the three questions MAIA answers don't shape data the same way:

10 The parser — turning COBOL into structure

Two engines behind one interface, and a compiler you have to build yourself.

parser.py exposes parse_all_cobol() / parse_all_jcl() and internally picks between two implementations of the same job:

  • Regex fallback — strips COBOL's fixed-format sequence numbers (columns 1–6), tracks IF/END-IF depth line-by-line with a running counter, and pattern-matches CALL '...'. About 80% accurate — multi-line statements and anything textually unusual can fool it.
  • Real AST — a compiled tree-sitter grammar. Walks the actual parse tree, so a CALL split across three lines, or a comment containing the word IF, can't confuse it.
Why this needed real engineering, not a pip install

tree-sitter-languages — the usual shortcut for prebuilt grammars — does not ship COBOL at all. Not "outdated," absent: running nm on its compiled languages.so shows no tree_sitter_cobol symbol in any version. There's no tree-sitter-cobol package on PyPI either. The only way to get AST parsing was cloning yutaro-sakamoto/tree-sitter-cobol and compiling it locally with Language.build_library() — which only exists in tree-sitter==0.21.3; 0.22+ removed it, so that version is pinned in requirements.txt with a comment explaining why.

The grammar's real shape was the second surprise. The natural assumption — an if_statement node that contains its conditional body — is wrong for this grammar. IF/EVALUATE are represented as flat sibling markers in the statement stream:

actual parse tree for BILLING.CBL's PROCESS-CUSTOMERS-PARA (dumped, not assumed)
call_statement   CALL 'TAXCALC'   USING CUST-PLAN
if_header        IF WS-BILL-AMOUNT > WS-THRESHOLD
call_statement   CALL 'CREDITVAL' USING CUST-ID     ← conditional
END_IF
call_statement   CALL 'CUSTMGMT'  USING CUST-ID     ← unconditional! after END_IF

So "is this call conditional" can't be answered by walking into a nested node — it has to be a depth counter threaded across a sibling list, incrementing at if_header/evaluate_header and decrementing at END_IF/END_EVALUATE, exactly mirroring what the regex fallback already did with text lines — just now driven by real tokens instead of regex matches on raw text.

That rewrite paid for itself immediately: the regex parser had been silently mis-flagging BILLING's unconditional CALL 'CUSTMGMT' as conditional (a stale if-depth counter that never fully unwound). The AST version gets it right — see Bugs found & fixed.

11 How tree-sitter grammars actually work

The pipeline behind one line in build_cobol_grammar.sh — from a JavaScript file to a real Python AST.

The core idea to hold onto: a grammar is a blueprint, not a house. A blueprint precisely describes rooms, walls, and doors — but you can't live in a blueprint. Something has to build the house from it before it's useful. Everything below is that build process, for COBOL, traced through the exact repo and commands used in this project.

What's in the tree-sitter-cobol repository

tree-sitter-cobol/ grammar.js # the blueprint — human-written rules for COBOL syntax package.json # Node.js metadata — declares tree-sitter-cli as a dependency bindings/ # wrapper code so Node.js/Rust/etc. can use this grammar queries/ # .scm files for editor syntax highlighting — irrelevant to us test/, sample/ # test COBOL files + expected parse trees src/ grammar.json # grammar.js, pre-compiled to plain JSON node-types.json # schema describing every node type the grammar can produce parser.c # 30MB(!) of GENERATED C — the actual parsing tables scanner.c # hand-written C helper, for tokens too tricky to declare

Only two files matter for what this project actually does: src/parser.c and src/scanner.c. Everything else is documentation, editor tooling, or scaffolding for languages other than Python.

grammar.js is a specification, not a parser

grammar.js — a rule, not executable logic
program_definition: $ => seq(
  $.identification_division,
  optional($.environment_division),
  optional($.data_division),
  optional($.procedure_division),
),

This cannot parse anything by itself. It's not even really "run" in the normal sense — it's read by a separate tool, next, that turns it into something that actually can.

The parser generator — how parser.c gets created

tree-sitter generate (part of the tree-sitter-cli npm package) does three things:

  1. Reads grammar.js — actually runs it under Node.js, since it's a small JS program that calls a grammar({...}) function and returns a description object.
  2. Builds a parsing automaton from the rules — real compiler-construction work: computing states, transitions, and conflict resolutions for every sequence of tokens the grammar allows.
  3. Emits it all as portable C — the states become giant static arrays, plus one key function, tree_sitter_COBOL(), that hands back a pointer to those tables.
Why generate C instead of hand-writing it

Scale. This grammar's generated parser.c is 30 megabytes of C — genuinely too large to hand-maintain. The author writes perhaps a thousand readable lines of grammar.js; the generator mechanically expands that into tens of thousands of parsing-table entries. Same reason yacc/bison/ANTLR exist elsewhere: write the rules, let a tool derive the machine.

parser.c itself is grammar-specific data, not a full standalone parsing program — think of it as a rulebook. Tree-sitter's actual generic parsing algorithm (walk tokens, consult tables, build tree nodes) lives once, centrally, in tree-sitter's own runtime, reused for every language. parser.c only supplies COBOL's specific tables plus that one entry-point function the runtime calls to get them.

What Language.build_library() actually does — verified, not assumed

backend/grammars/build_cobol_grammar.sh — the one line that matters

python3 -c "

Confirmed directly this session by running it and inspecting the result with nm (a tool that lists the named symbols inside a compiled binary):

  • Looks for src/parser.c — required.
  • Looks for src/scanner.c — optional, compiled too if present.
  • Invokes a C compiler (cc/clang/gcc, via Python's own compiler machinery) on just those two files, then links the result into one shared library at the output path given.

It never touches grammar.js, grammar.json, node-types.json, queries/, package.json, bindings/, or the README. It does not run tree-sitter generate — it assumes parser.c already exists on disk. That's exactly why the grammar's author committed a 30MB generated file to the repo: so someone with no Node.js installed — just this project — can still build a working parser with nothing but git clone and a C compiler.

What a shared object (.so) actually is

Compiled machine code — real CPU instructions for your exact processor and OS, not portable text like a .py or .js file. "Shared" means many different running programs can all load and use the same copy of it from disk at once, instead of each program needing its own private baked-in copy.

Python can't execute parser.c directly — it's not a C interpreter, and C has to be compiled for a specific CPU architecture first (an ARM Mac and an x86 Linux server need genuinely different binaries from identical source). Once compiled into cobol.so, Python can reach it, via ctypes — the bridge between portable C source text and something Python can actually call.

How Python loads and uses cobol.so

backend/parser.py
from tree_sitter import Language, Parser

Language(path, "COBOL") opens cobol.so (via ctypes's dynamic loader), looks up the symbol tree_sitter_COBOL — built from the exact name passed in, which is why case matters (this genuinely tripped things up once: "cobol" lowercase fails with "symbol not found," because the grammar's real internal name is COBOL) — calls it, and gets back a pointer to the grammar's tables. parser.set_language() tells tree-sitter's generic runtime (bundled inside the Python package itself) which tables to use; parser.parse() runs that engine against real COBOL source and hands back a walkable Tree.

The one thing worth internalizing: build_cobol_grammar.sh only ever performs the middle step — C source → .so. Four misconceptions worth ruling out explicitly

  • ❌ grammar.js is directly used by the Python application. It isn't — Python never opens, imports, or reads it.
  • ❌ parser.c is generated by build_cobol_grammar.sh. It isn't — the script never runs tree-sitter generate; it clones a repo that already contains a pre-generated parser.c.
  • ❌ Language.build_library() does grammar analysis or code generation. It doesn't — it's "just" a C compiler invocation: find parser.c (+ scanner.c), compile, link.
  • ✅ cobol.so is the only artifact the running code actually touches. Everything upstream of it is provenance — worth understanding, never touched at runtime.

Why a dataclass instead of a plain dict

COBOLProgram — every field, and what it holds
@dataclass
class COBOLProgram:
    name:              str        = ""          # PROGRAM-ID, e.g. "PAYROLL"
    author:            str        = ""          # from the AUTHOR paragraph
    date_written:      str        = ""
    description:       str        = ""          # first ~3 lines of header comments
    calls:             list[str]  = field(default_factory=list)  # every program this one CALLs
    conditional_calls: list[str]  = field(default_factory=list)  # the subset inside an IF/EVALUATE
    reads:             list[str]  = field(default_factory=list)  # dataset names from ASSIGN TO
    writes:            list[str]  = field(default_factory=list)  # from WRITE/REWRITE statements
    copybooks:         list[str]  = field(default_factory=list)  # names from COPY statements
    paragraphs:        list[str]  = field(default_factory=list)  # every named paragraph label
    complexity_score:  float      = 0.0
    lines:             int        = 0
    parser_mode:       str        = "regex"    # "ast" or "regex" — which branch actually ran
    source_path:       str        = ""

@dataclass is a decorator that auto-generates a constructor from the field list above it — write COBOLProgram(name="PAYROLL") and every other field takes its default. Each list field uses field(default_factory=list) rather than just = [] — this avoids a classic Python trap: a plain mutable default like [] would be the same list object shared by every instance, so appending to one program's .calls would silently also affect every other program ever created. default_factory calls list() fresh for each new instance instead. A plain dict couldn't offer any of this — no type hints, no auto-generated constructor, and no protection against the shared-mutable-default bug — and a typo like prog["cals"] would only surface as a silent wrong answer, whereas prog.cals is an immediate, obvious AttributeError.

to_dict() — why it exists at all
def to_dict(self) -> dict:
    return {"name": self.name, "calls": self.calls, ...}

Every downstream consumer — graph.py's loaders, and eventually FastAPI's JSON responses — wants a plain dict, not a custom class instance (JSON serialization, and Neo4j's driver, don't know what a COBOLProgram is). to_dict() is the one deliberate conversion point between "a rich, type-checked Python object used while parsing" and "a plain, universally-understood data structure used everywhere else."

COBOLParser.parse_file() — the entry point

the dispatcher
def parse_file(self, path: str) -> COBOLProgram:

    prog = COBOLProgram(source_path=path, lines=text.count("\n"))
    if _AST_AVAILABLE:

_parse_regex() — the fallback, tracking IF-depth by hand

stripping COBOL's fixed-format sequence numbers first
for line in raw_lines:
    stripped = line[6:] if len(line) > 6 else line

Classic fixed-format COBOL reserves columns 1–6 of every line for a sequence number (a holdover from punch cards) — line[6:] is Python slice notation meaning "everything from index 6 to the end," which discards those 6 characters before any pattern matching happens.

the depth counter — the same trick tree-sitter's walker uses, just on raw text
if_count  = len(re.findall(r"\bIF\b",       s))
endif_cnt = len(re.findall(r"\bEND-IF\b",   s))
if_depth  = max(0, if_depth + if_count - endif_cnt)
in_cond   = (if_depth > 0 or eval_depth > 0)

\b in a regex means a word boundary — without it, r"IF" would also match inside words like "MODIFY." Each line updates a running counter: every IF seen increments it, every END-IF decrements it, clamped at 0 with max(0, ...) so it can never go negative. Any CALL found while this counter is above zero gets marked conditional. This is exactly the same conceptual trick the AST walker uses — a depth counter threaded across a sequence — just driven by regex matches on text lines instead of real parse-tree siblings, which is why it's less reliable (a comment containing the word "IF", or a statement split across lines, can throw it off).

_score() — the 0–10 complexity number

five weighted, capped contributions
score += min(prog.lines / 500 * 3, 3.0)          # lines of code,   capped at 3
score += min(len(prog.calls) * 0.8, 3.0)         # external calls,  capped at 3
score += min(len(prog.paragraphs) * 0.25, 1.5)   # paragraph count, capped at 1.5
score += min(ifs * 0.08, 1.5)                    # IF count,        capped at 1.5
score += min(gotos * 0.3, 1.0)                   # GOTO count,      capped at 1.0

Each factor is capped independently before summing (so one runaway metric — say, 500 IFs — can't single-handedly dominate the score), and the grand total is capped at 10 as a final safety net. The weights (3, 3, 1.5, 1.5, 1) reflect a judgment call about what actually makes COBOL risky to touch: raw size and how many other programs it integrates with matter most; branching and paragraph count matter less; this is a heuristic, not a formal metric, and the numbers in the code are exactly that judgment call made explicit and readable.

JCLParser — no AST needed, JCL is much simpler

JCL doesn't get a tree-sitter grammar at all — it's parsed with plain line-by-line regex, because its structure is far more rigid (fixed //KEYWORD PARAM syntax, no nested control flow to get wrong). It reads metadata straight out of specially-formatted comment lines (//* SCHEDULE: 1ST OF EVERY MONTH...), EXEC PGM= for which program a step runs, and DSN= for which datasets a step touches.

base = datetime.now() - timedelta(days=14)

inner loop 1 — LPAR readings, every 30 minutes of every day
for hour in range(24):
    for lpar, bases in LPAR_BASE.items():
        m    = bases[hour]
        mips = int(m + random.gauss(0, m*0.06))
        cpu  = round(min(99.9, mips/m*65 + random.gauss(0,3)), 1)
        ts   = d.replace(hour=hour, minute=random.randint(0,29), second=0)

bases[hour] looks up that LPAR's expected MIPS for this hour. random.gauss(0, m*0.06) draws one random number from a Gaussian (bell-curve) distribution centered at 0 with a spread of 6% of the base value — added to the base, this gives realistic-looking noise (small wobbles far more often than huge ones, matching how real workloads actually fluctuate) rather than random.uniform()'s equally-likely-anywhere noise, which would look obviously fake — occasional wild swings, no clustering around the expected value. cpu derives from that same MIPS value as a rough percentage, plus its own small independent noise term, capped at 99.9 so it never technically claims "100%+ CPU." d.replace(hour=hour, minute=random.randint(0,29), second=0) takes the day d and sets a specific hour/minute/second on it — a random minute within the first half of the hour, since real readings arrive every 30 minutes, not on a perfect clock tick.

inner loop 2 — job runs, only on the days each job actually runs
for job, lpar, base_mins, base_mips in JOB_PATTERNS:

This mirrors the real JCL schedule: NIGHTLY runs every single day, but PAYJOB and BILLJOB (per their JCL header comments) only run on the 1st and 15th of the month — the continue statement skips straight to the next iteration of the loop for every other day, for every job except NIGHTLY. is_failure is a compound boolean condition: BILLJOB, specifically on the 1st, specifically in April or June (the quarter-end months the runbook's INCIDENT-002 describes), with a 70% chance — this is how the seeded history includes the exact CICS-contention failure story that the runbook and JCL comments both reference, without hand-writing specific rows.

15 simulator.py, line by line

Why a fake mainframe exists, and how it fakes one convincingly.

Why a simulator exists at all

A real IBM mainframe would supply this project's data through three real systems: SMF (System Management Facility — the mainframe's own black-box flight recorder, logging every job's return code, CPU seconds, elapsed time), RMF (Resource Measurement Facility — LPAR-level performance snapshots), and z/OSMF (a REST API into z/OS for reading datasets/jobs programmatically). None of those exist in a laptop prototype — so simulator.py generates data shaped exactly like what those systems would produce, on a highly compressed timescale (a full day's rhythm in minutes), so the rest of the app — the charts, the alert rules, the chat's SQL queries — can be built and demoed against something that behaves like the real thing, with nothing else in the codebase needing to know the difference. Swapping this file for real z/OSMF calls later would require zero changes anywhere else.

BASE — 24 numbers per LPAR, one per hour

MIPS = "millions of instructions per second" — a mainframe's basic workload unit
BASE = {
    "LPAR-1": [2100,4100,4200,2200, ...],  # index 0 = midnight, index 13 = 1 PM
    ...
}

Each LPAR gets a 24-entry list — its expected MIPS at each hour of the day. These aren't random: LPAR-1 (payroll) spikes around 1–3 AM (PAYJOB's window), LPAR-2 (billing) around 3–6 AM, LPAR-3 (reporting) peaks hardest of all at 6–9 AM (NIGHTLY). Workloads change through the day because that's what batch scheduling actually looks like on a real mainframe estate — different jobs owning different windows, exactly matching the JCL schedules in the sample data. LABEL is just a parallel dict of human-readable names for each LPAR ID, used for display.

AnomalyState — a tiny countdown-timer class

the whole class
class AnomalyState:
    def __init__(self):
        self.active: dict[str, int] = {}   # anomaly_id → remaining_cycles

    def inject(self, aid, cycles=4):
        self.active[aid] = cycles          # start (or restart) a countdown

    def tick(self):
        done = [k for k, v in self.active.items() if v <= 1]
        for k in done: del self.active[k]
        for k in self.active: self.active[k] -= 1

    def has(self, aid):
        return aid in self.active

active maps an anomaly's name to how many more 10-second cycles it should stay in effect. inject() starts a countdown. tick() runs once every cycle: first collect every anomaly whose count is about to hit zero (v <= 1) into a done list, delete those, then decrement everything still remaining by one. Building the deletion list before deleting is deliberate — you can't safely remove keys from a dict while a for loop is actively iterating over that same dict in Python; it would raise a RuntimeError. has() is just a membership check, used everywhere else to ask "is this anomaly currently active?"

JOB_SCHEDULE — cycles, not clock times

why "every N cycles" instead of a cron schedule
JOB_SCHEDULE = [
    ("NIGHTLY",  "LPAR-3", 141, 7100, 36),   # every 36 cycles = 6 min
    ("PAYJOB",   "LPAR-1", 108, 4100, 60),   # every 60 cycles = 10 min
    ("BILLJOB",  "LPAR-2", 133, 5200, 72),   # every 72 cycles = 12 min
]

Real PAYJOB/BILLJOB run once a month; NIGHTLY runs once a day. Waiting a literal month to see a demo job complete would make the app impossible to show anyone. Instead of a real calendar schedule (cron), the simulator just counts its own 10-second cycles and fires a job whenever cycle % every_n == 0 — a plain integer counter is far simpler than reimplementing calendar logic, and "every N cycles" compresses a month down to minutes without needing to fake dates at all.

rolling the anomaly dice, once per cycle
rand = random.random()          # a float, uniformly random between 0.0 and 1.0
if rand < 0.08:
    _anomaly.inject("lpar3_spike", cycles=4)   # 8% chance, ~40s spike
elif rand < 0.13:
    _anomaly.inject("rha_risk", cycles=6)      # next 5%  (0.08–0.13)
elif rand < 0.16:
    _anomaly.inject("billjob_fail")            # next 3%  (0.13–0.16)

This is the standard trick for picking one of several weighted random outcomes from a single dice roll: each elif claims the next slice of the 0–1 range, so the three anomalies get 8%, 5%, and 3% probability respectively (16% combined chance of something happening each cycle), and 84% of cycles inject nothing at all.

generating one LPAR reading, with realistic noise
base  = BASE[lpar][hour]
noise = random.gauss(0, base * 0.06)      # Gaussian, not uniform — see below
mips  = max(500, int(base + noise))

if lpar == "LPAR-3" and _anomaly.has("lpar3_spike"):
    mips = int(mips * 1.35)             # +35% during a spike
if _anomaly.has("rha_risk"):
    mips = int(mips * 1.20)             # all 3 LPARs +20% at once

cpu = round(min(99.9, mips / BASE[lpar][hour] * 65 + random.gauss(0,3)), 1)

Why Gaussian noise, not uniform: random.uniform(-x, x) makes every value in that range equally likely — a huge swing is just as probable as a tiny one, which looks obviously synthetic on a chart (jagged, no clustering). random.gauss(0, sigma) draws from a bell curve — small deviations from the average are common, large ones are rare — which is how real-world measurement noise actually behaves, so the resulting chart looks like a genuine workload rather than random static. cpu is derived from the ratio of actual-to-base MIPS scaled by a rough constant (65), plus its own small independent noise term, capped at 99.9. Both anomaly multipliers apply before this reading is inserted — insert_lpar(lpar, label, int(mips*0.92), mips, cpu) writes it to SQLite exactly like the real z/OSMF-replacement it is.

generating a job completion — and the BILLJOB failure specifically
for job, lpar, base_elapsed, base_mips, every_n in JOB_SCHEDULE:
    if _cycle % every_n != 0:
        continue          # not this job's cycle — skip

    is_failure = (job == "BILLJOB" and _anomaly.has("billjob_fail"))
    elapsed = base_elapsed + random.gauss(0, base_elapsed * 0.08)
    mips    = base_mips    + random.gauss(0, base_mips * 0.05)

        mips    *= 1.6

                   mips=int(mips), rc=8, status="FAILED",

The elapsed-time doubling (×2.1) and MIPS increase (×1.6) aren't arbitrary — they're modeling exactly what INCIDENT-002 in the runbook describes: BILLJOB stalls retrying against a CICS-held dataset, burning extra CPU while it waits, and the exact error text ("CHARGE.DETAIL.DATA HELD BY CICS TRANSACTION CHRG...") is copy-identical to what the runbook and the sample SMF JSON both describe — so a chat question about this failure gets consistent facts whichever store answers it. _anomaly.active.pop("billjob_fail", None) removes the flag immediately after firing once — this anomaly is a single event, not a sustained condition like the CPU spike, so it must not fire again on a future BILLJOB cycle just because it's still sitting in the active dict. rc (return code) 0 means success, 8 means a real failure — matching actual mainframe convention (0=OK, 4=warning, 8+=error), which is exactly what smf_store.py's rc column and alerts.py's failure rule both key off.

16 alerts.py, line by line

Five rules, zero LLM calls, every threshold and every query clause explained.

Why rules, not an LLM — and why SQL is enough

An LLM call costs money, takes seconds, and can fail or rate-limit. A dashboard that's checking "is anything on fire right now" every 30 seconds, forever, cannot depend on any of that — it needs an answer that's instant, free, and deterministic. Every one of these five questions ("is CPU over 85%?", "did a job return a nonzero code?") is something a plain SQL WHERE clause answers exactly and immediately — there's no ambiguity to reason about, so reaching for an LLM here would only add latency, cost, and a new failure mode for zero benefit. (React never reads SQLite directly, either — a browser can't open a database file; it only ever talks to main.py's HTTP endpoints, which is the whole reason a backend server exists at all. See Concepts primer.)

_sql() — the one shared query helper

every rule funnels through this
def _sql(query: str, params=()) -> list[dict]:
    with sqlite3.connect(DB_PATH) as c:
        c.row_factory = sqlite3.Row
        return [dict(r) for r in c.execute(query, params).fetchall()]

Same sqlite3.Row → dict pattern as smf_store.py — every rule function gets back a plain list of dicts to loop over, never raw tuples.

Rule 1 — rule_lpar_cpu_high()

clause by clause
SELECT lpar, peak_mips, cpu_pct, ts
FROM lpar_performance
WHERE ts >= datetime('now','-2 minutes')   -- only readings from the last 2 minutes
  AND cpu_pct > 85                     -- the actual threshold
ORDER BY cpu_pct DESC

datetime('now','-2 minutes') computes "2 minutes before right now" — combined with >=, the WHERE keeps only rows timestamped within that recent window, so a CPU spike from an hour ago can never resurrect itself as a "current" alert. In Python, each matching row becomes one alert dict: "severity": "CRITICAL" if r["cpu_pct"] > 95 else "HIGH" — a single conditional expression picking between two severities based on just how far over the threshold the reading is. "id": f"cpu_high_{r['lpar']}" is deliberately keyed by LPAR only, not by timestamp — so the same ongoing spike keeps producing the same alert id across repeated 30-second evaluations, rather than a new "alert" every cycle.

Rule 2 — rule_job_failed()

clause by clause
SELECT job, date, start_time, rc, error, ts
FROM job_history
WHERE rc != 0                          -- any nonzero return code = a failure
  AND ts >= datetime('now','-30 minutes')  -- only recent failures
ORDER BY ts DESC

Every match is CRITICAL, unconditionally — a job that actually failed always deserves top severity, unlike CPU (a spectrum). (r['error'] or '')[:70] truncates the error message to 70 characters for a short alert card — r['error'] or '' guards against a None value (Python would otherwise crash trying to slice None).

Rule 3 — rule_rha_spike() — a subquery, explained

clause by clause, inside-out
SELECT lpar,
       ROUND(AVG(peak_mips)) AS rolling_avg,
       MAX(peak_mips)        AS top_mips,
       MAX(ts)               AS ts
FROM (
    SELECT lpar, peak_mips, ts FROM lpar_performance
    ORDER BY ts DESC LIMIT 12          -- innermost: the 12 most recent readings, ANY lpar
)
GROUP BY lpar                          -- then split those 12 rows by which LPAR they belong to
HAVING rolling_avg > 9000               -- keep only groups whose average exceeds the tier boundary

A query inside another query's FROM is a subquery — SQL evaluates the innermost one first, then treats its result as if it were a regular table for the outer query. Here, the inner query grabs the 12 most recent LPAR readings across the whole estate (roughly the last 2 minutes at 3 LPARs reporting every 10s); the outer query groups those by LPAR and averages each group's peak_mips — approximating a "rolling 4-hour average" (the real R4HA billing metric IBM uses) on this compressed demo timescale. HAVING is WHERE's counterpart for filtering after grouping/aggregating — plain WHERE can't reference an aggregate like AVG(...) because that value doesn't exist until the grouping is done.

Rule 4 — rule_job_overtime() — a self-join

the table joined to itself
SELECT h.job, h.elapsed_mins, h.ts, AVG(h2.elapsed_mins) AS avg_mins
FROM job_history h
JOIN job_history h2 ON h2.job = h.job     -- pair every row with every OTHER run of the same job
WHERE h.ts >= datetime('now','-10 minutes') AND h.rc = 0
GROUP BY h.job, h.elapsed_mins, h.ts
HAVING h.elapsed_mins > avg_mins * 1.5 AND avg_mins > 0

job_history h JOIN job_history h2 ON h2.job = h.job is a self-join — the same table appears twice under two different aliases (h and h2), letting one row of a job's history be compared against every historical row of that same job (to compute its average), not just itself. GROUP BY h.job, h.elapsed_mins, h.ts effectively re-isolates one specific recent run per group (since that combination is unique per real row) while still letting AVG(h2.elapsed_mins) range freely over every historical run of that job — the HAVING then keeps only runs that took more than 1.5× their own job's typical time.

Rule 5 — rule_lpar_contention() — the only rule that queries Neo4j, not SQLite

Cypher, not SQL — because this is a relationship question
MATCH (j1:Job)-[:RUNS_ON]->(l:LPAR)<-[:RUNS_ON]-(j2:Job)
WHERE j1.name < j2.name        -- avoids reporting both (A,B) and (B,A)
RETURN j1.name AS job1, j2.name AS job2, l.name AS lpar

This pattern reads as: find an LPAR with two different jobs both pointing at it via RUNS_ON. j1.name < j2.name is a simple string comparison used purely to break symmetry — without it, the same pair would come back twice (once as (PAYJOB, BILLJOB), once as (BILLJOB, PAYJOB)), since Cypher's undirected-looking pattern actually matches both directions. This is the one rule wrapped in its own try/except returning an empty list on failure — unlike the SQLite rules, a Neo4j outage shouldn't take down the other four rules (each is independently guarded again inside evaluate_all() too).

evaluate_all() — running every rule, then deduplicating

the full function
def evaluate_all() -> list[dict]:
    all_alerts = []
    for rule in [rule_lpar_cpu_high, rule_job_failed, rule_rha_spike,
                 rule_job_overtime, rule_lpar_contention]:
        try:
            all_alerts.extend(rule())
        except Exception as e:
            print(f"Alert rule error ({rule.__name__}): {e}")

    seen: dict[str, dict] = {}
    sev_order = {"CRITICAL":0, "HIGH":1, "MEDIUM":2, "LOW":3}
    for a in all_alerts:
        aid = a["id"]
        if aid not in seen or sev_order[a["severity"]] < sev_order[seen[aid]["severity"]]:
            seen[aid] = a

    result = sorted(seen.values(), key=lambda x: sev_order[x["severity"]])
    for a in result: a["color"] = SEV[a["severity"]]
    return result

Each rule runs inside its own try/except — one broken rule (a bad query, a down database) only loses that rule's alerts for this cycle, never crashes the whole evaluation. Deduplication: seen is a dict keyed by alert id; for each alert, it's only replaced if either this id hasn't been seen yet, or the new one is more severe (a smaller number in sev_order — CRITICAL=0 is "smallest," i.e. sorts first) — this matters because rules can theoretically produce the same id at different severities across re-evaluations, and the more urgent one should always win. Severity ordering is exactly that dict: CRITICAL < HIGH < MEDIUM < LOW as plain integers, so sorted(..., key=lambda x: sev_order[...]) naturally places the most urgent alerts first without any custom comparison logic. Color mapping (SEV = {"CRITICAL": "red", "HIGH": "orange", ...}) is attached last, purely for the React dashboard's styling — the rules themselves never think in terms of color.

The grounding isn't a personality trait the model has — it's a structural fact: made-up numbers are literally not available to fall back on.

Rules 4 and 5 are worked examples of the exact Cypher/SQL shape a good answer needs — not because the model can't write Cypher without help, but to bias it toward the traversal patterns (*1..6 variable-length paths for impact analysis, averaging recent rows for billing) that this specific schema rewards, rather than a shallower query that happens to also parse.

    if not resp.tool_calls:
        return resp.text or "No response."

    for tc in resp.tool_calls:
        tool = tool_map.get(tc["name"])
        result_text = str(await tool.ainvoke(tc["args"])) if tool else ...
        messages.append(ToolMessage(content=result_text, tool_call_id=tc["id"]))

return "Reached tool call limit — try rephrasing your question."

ainvoke() is the async version of "call the model and wait for a reply" — a for async, matching every other await in this file. Each iteration: ask the model, append its reply to the running conversation (so it remembers what it just said next iteration), then check resp.tool_calls — LangChain's normalized list of "the model wants to call these tools," regardless of exactly how Gemini's own API represents that internally. Empty means the model is done reasoning and has a final answer — resp.text (not resp.content directly) is used because some models return structured content blocks instead of a plain string; .text normalizes either shape, a fix from Bugs found & fixed. If there are tool calls, each one is actually executed — tool.ainvoke(tc["args"]) makes the real network call to the real MCP server, which runs the real query against the real database — and the result comes back as a ToolMessage the model will see on its next iteration of this same loop. The range(10) cap exists so a model stuck in a query-refine-query-refine cycle can't loop forever and silently burn quota; ten rounds is generous for any question this schema is built to answer.

Exactly how Gemini decides what to query — there's no magic, just the schema

The model isn't told "for CPU questions use SQL" — it infers this itself, purely from reading the SCHEMA block: it sees lpar_performance(...,cpu_pct) lives in SQLite, so a CPU question becomes a sqlite_query call; it sees (Program)-[:CALLS]->(Program) lives in Neo4j, so an impact question becomes a neo4j_query call with real Cypher it writes on the spot; it sees ChromaDB "contains runbooks, incidents," so a "why did X fail" question becomes a chromadb_search call. Rule 3 ("call multiple tools when a question spans domains") is why a single question can trigger 2–3 sequential tool calls in one conversation turn — see the full worked trace in End-to-end traces.

_lpar_context() — Cypher, translated to plain English before Gemini ever sees it

the query
MATCH (j:Job)-[:RUNS_ON]->(:LPAR {name:$l})
OPTIONAL MATCH (dep:Job)-[:TRIGGERS]->(j)
OPTIONAL MATCH (j)-[:TRIGGERS]->(nxt:Job)
RETURN j.name AS name, j.schedule AS schedule, j.sla AS sla,
       collect(DISTINCT dep.name) AS depends_on,
       collect(DISTINCT nxt.name) AS triggers

Read top to bottom: first find every Job that runs on the LPAR named in $l (a query parameter, not a string pasted into the query text — same injection-safety principle as SQL's ? placeholders). Then OPTIONAL MATCH — unlike a plain MATCH, this won't throw the whole row away if no match exists; a job with no dependency just gets null in that slot instead of vanishing entirely. The two OPTIONAL MATCH clauses find, respectively, any job that triggers this one (its dependency) and any job this one triggers next. collect(DISTINCT ...) gathers every matching value into a single list per job — necessary because a job could plausibly have more than one dependency, and Cypher would otherwise return one row per combination rather than one row per job.

Python then turns each row into one plain-English bullet:

the conversion
for r in rows:
    deps = ", ".join(d for d in r["depends_on"] if d) or "none"
    trig = ", ".join(t for t in r["triggers"]  if t) or "none"
    lines.append(f"- {r['name']}: scheduled {r['schedule']}, SLA {r['sla']}, "
                 f"depends on [{deps}], triggers [{trig}]")
# → "- NIGHTLY: scheduled Every night 06:30 AM, SLA 09:00 AM, depends on [PAYJOB, BILLJOB], triggers [none]"

The if d filter drops any None entries the OPTIONAL MATCH could have produced, and or "none" handles the case where the resulting list is empty entirely. Rows get converted to a plain sentence — not handed to Gemini as raw JSON/Cypher-result structure — because a model reasons more reliably over natural language it can directly quote back than over nested data it has to first mentally re-parse; this is a small but deliberate choice, not an afterthought.

_runbook_context() — retrieval-augmented generation (RAG), in miniature

RAG just means: before asking a model to answer something, first retrieve real, relevant documents (here, via semantic search — see vector_store.py) and put their actual text directly into the prompt, so the model's answer is grounded in real source material instead of only what it happened to memorize during training.

the whole function
def _runbook_context(alert: dict) -> str:
    query = f"{alert.get('name','')} {alert.get('message','')}"
    hits = vector_store.search(query, n=2)
    if not hits:
        return "(no relevant runbook entries found)"
    return "\n\n".join(
        f"[{h['source']}, relevance {h['relevance']}]\n{h['text']}" for h in hits)

The alert's own name and message become the search query — e.g. "LPAR CPU Near Capacity LPAR-3 at 99.9% CPU (7,200 peak MIPS)" — and vector_store.search() (semantic search, meaning-based, not exact keyword matching) returns the top 2 most relevant runbook chunks, each carrying a relevance score (how confident the match is). Both get concatenated, source and score included, directly into the context block the model reads.

_root_cause() — why ExceptionGroups happen, and why they're unwrapped
def _root_cause(exc: BaseException) -> BaseException:
    while isinstance(exc, BaseExceptionGroup) and exc.exceptions:
        exc = exc.exceptions[0]
    return exc

ExceptionGroup is a Python feature for when multiple things fail at once inside concurrent code — anyio (the async library underneath the MCP client) wraps errors from its internal task groups this way, sometimes several layers deep, so a single real error (say, a Gemini 429) can arrive wrapped in two or three nested ExceptionGroups. Printed directly, that just reads as "unhandled errors in a TaskGroup" — true, but useless to a user. This while loop repeatedly unwraps one layer (exc.exceptions[0], the first nested exception) until it hits something that isn't a group anymore — the actual root cause — and that's what gets shown.

21 CORS, from scratch

Why a browser can refuse a request that a server already answered with 200 OK — and why that's a feature, not a bug.

What an "origin" actually is

An origin is the combination of protocol + domain + port — http://localhost:5173 and http://localhost:8000 are different origins, even though they're both "localhost," because the port is part of the origin too. To a browser, these are as different as two completely unrelated websites.

The Same-Origin Policy — and the bank-website reason it exists

By default, a browser refuses to let JavaScript running on one origin read a response fetched from a different origin. Here's exactly why that rule has to exist: imagine you're logged into your bank at mybank.com — your browser is holding a valid session cookie for it. You then visit a completely unrelated, malicious website in another tab. If that page's JavaScript could freely fetch("https://mybank.com/api/balance") and actually read the response, your browser would automatically attach your real bank session cookie to that request (browsers attach cookies based on the target domain, not who's asking) — and the malicious page would get your balance, or worse, could submit a funds transfer, all silently, just because you had your bank tab open somewhere else. The Same-Origin Policy exists specifically to make that attack impossible: no page can read another origin's responses unless that origin explicitly opts in.

Why Postman "just works" but a browser blocks the same request

The Same-Origin Policy is enforced by the browser, not the server — it's a rule about what JavaScript running in a page is allowed to read. Postman isn't a web page with a same-origin concept at all; it's a standalone application making direct HTTP requests, with no browser security sandbox involved, so nothing stops it from reading any response from anywhere. The server, in both cases, actually processes the request and sends back 200 OK either way — CORS never stops the server from doing its job. It stops the browser from handing that already-arrived response to your JavaScript code.

CORSMiddleware and what it actually adds

This is why the request "succeeding" on the server side (visible in server logs, in FastAPI's own /docs) doesn't mean your JavaScript ever sees the data — the browser can throw the response away before your code ever touches it. The fix is CORSMiddleware: it makes the server add a specific response header, Access-Control-Allow-Origin, explicitly listing which origins are allowed to read its responses. The browser checks that header itself, after the response arrives, before deciding whether to let your JavaScript's fetch() promise actually resolve with the data.

ParameterWhat it controls
allow_originsExactly which origins get the Access-Control-Allow-Origin header back — here, ["http://localhost:5173", "http://localhost:3000"], the two ports Vite's dev server might use
allow_methods["*"] — every HTTP method (GET, POST, etc.) is allowed from those origins
allow_headers["*"] — any request header the frontend sends is allowed through

Preflight requests — the OPTIONS call you never wrote

For anything beyond the simplest requests (a POST with a JSON body counts), the browser doesn't even send your actual request first — it sends a preflight request: an OPTIONS method call to the same URL, essentially asking "if I were to send a real POST with these headers, would you allow it?" Only if the server's response to that OPTIONS call includes the right Access-Control-Allow-* headers does the browser then actually send your real request. CORSMiddleware handles responding to these OPTIONS requests automatically — nothing in main.py's own endpoint functions ever sees or handles an OPTIONS request directly.

What it would look like if this were missing

an actual browser console error, verbatim

Note what this error does not say — it never claims the server failed. The honest caveat: this project's dev setup mostly avoids needing it

frontend/vite.config.js
server: {
  proxy: { '/api': 'http://localhost:8000' }
}

Every fetch call in this codebase uses a relative path — fetch('/api/alerts'), never fetch('http://localhost:8000/api/alerts'). Vite's dev server proxy intercepts anything starting with /api and forwards it to port 8000 server-side, then relays the response back as if it came from port 5173 all along — so from the browser's point of view, it never actually made a cross-origin request in normal day-to-day use; the proxy hid the whole problem. CORSMiddleware is still correctly configured and still matters in real scenarios this dev proxy doesn't cover: opening /docs directly from a browser and testing an endpoint from there, a production deployment where the built frontend is served from a different origin than the API without a proxy in front of it, or any future code that fetches an absolute URL instead of a relative one.

22 React frontend — from zero web dev knowledge to every file

This section assumes you've never touched React, CSS-in-JS, or a JS build tool. Every concept before the file-by-file walkthrough exists so the code after it isn't just memorized syntax.

What a browser actually does with a web page

A browser reads three things: HTML (structure — "there's a button here"), CSS (appearance — "make it blue"), and JavaScript (behavior — "when clicked, do X"). Traditionally you write all three by hand, in separate files. React changes the shape of the first two: instead of writing static HTML and separately writing JS that pokes at it, you write JavaScript functions that describe what the HTML should look like right now, and React keeps the actual on-screen page in sync with what those functions return, automatically, whenever the underlying data changes.

What a "component" is — a function that returns UI

the simplest possible component
function Greeting() {
  return <h1>Hello, MAIA</h1>
}

That's genuinely it — a component is a plain JavaScript function whose job is to return a description of some UI. <h1>Hello, MAIA</h1> isn't a string and isn't real HTML yet — it's JSX, a syntax extension that lets you write HTML-shaped tags directly inside JavaScript. A build tool (below) transforms JSX into plain JavaScript function calls before it ever reaches a browser; you never write or see that translated form.

Props — how a component receives information from its caller

real code from this project — App.jsx's Chip component
function Chip({ label, value, color }) {
  return (
    <div>
      <div>{value}</div>
      <div>{label}</div>
    </div>
  )
}
// used like: <Chip label="Programs" value={6} color="teal" />

Props ("properties") are how a parent hands data down into a child component — exactly like arguments to a function, because that's structurally what they are. {{ label, value, color }} is JavaScript's destructuring syntax, pulling three named values straight out of the single object React passes every component. Curly braces {value} inside the JSX are how you drop a real JavaScript value into otherwise-HTML-looking markup — anything inside {} is evaluated as JavaScript and the result is shown.

State and hooks — a component's own memory

Props are handed down from outside. State is data a component owns and manages itself, that can change over time and cause the screen to re-render when it does. useState is the tool for this — a hook, meaning a special function that only works inside a component and lets it "hook into" React features:

the shape every stateful component in this app follows
const [tab, setTab] = useState('dashboard')
// tab     → the CURRENT value (starts as 'dashboard')
// setTab  → the ONLY correct way to change it

useState('dashboard') returns an array of exactly two things — the current value, and a function to change it — pulled apart with array destructuring (const [a, b] = ...). Calling setTab('chat') anywhere does two things: updates the stored value, and tells React "re-run this component's function and redraw whatever changed" — you never manually touch the actual on-screen DOM elements yourself; you just change the state and describe what the UI should look like for any given state, and React reconciles the difference.

useEffect — running code when a component appears (and cleaning up after)

the polling pattern every tab in this app uses
useEffect(() => {
  const load = () => { fetch('/api/alerts').then(r=>r.json()).then(setData) }
  load()                                    // run once immediately
  const t = setInterval(load, 30000)     // then again every 30 seconds
  return () => clearInterval(t)         // cleanup: stop polling if this component goes away
}, [])

useEffect runs some code as a side effect of rendering — anything that reaches outside pure "compute what to show" (a network call, a timer). The empty array [] as the second argument means "run this setup exactly once, when the component first appears, not on every re-render." The function returned from inside the effect is React's cleanup hook — called automatically if the component is ever removed from the screen, which is exactly why clearInterval(t) is there: without it, switching away from a tab wouldn't actually stop its background polling, silently leaking timers that keep firing forever.

What Tailwind CSS is — and why there's no separate .css file per component

Traditional CSS lives in its own file, with rules like .card { background: #0F1C2E; border-radius: 12px; } that you then reference by class name. Tailwind flips this: instead of naming your own classes, you compose pre-made utility classes directly in the markup, each doing one small, specific thing:

one real className from Dashboard.jsx, decoded
className="rounded-xl border border-[#1A2C47] bg-[#0F1C2E] p-4 flex items-start gap-4"
  rounded-xl        → border-radius: 0.75rem
  border            → border-width: 1px
  border-[#1A2C47]  → that specific border color (square brackets = an exact custom value)
  bg-[#0F1C2E]      → that specific background color
  p-4               → padding: 1rem on all sides
  flex              → display: flex
  items-start       → align-items: flex-start
  gap-4             → 1rem of space between flex children

Nothing here needs a separate stylesheet or a class name you invented — the visual design is legible directly from the markup itself, at the cost of long className strings. This is a stylistic choice, not a requirement of React itself — plenty of React apps use traditional CSS files instead.

The build tool — Vite, and what "npm run dev" actually does

A browser doesn't understand JSX, and doesn't want to download dozens of separate small JavaScript files one at a time. Vite is the tool that: runs a local dev server, transforms JSX into plain JS on the fly as files are requested, and (per vite.config.js) proxies anything starting with /api straight through to the FastAPI backend on port 8000 — see CORS, from scratch for why that proxy quietly avoids most cross-origin issues in dev. index.html is the one real static HTML file in the whole project — it contains almost nothing but an empty <div id="root"></div> and a <script> tag pointing at main.jsx; React fills that empty div with everything else, entirely from JavaScript.

How the frontend "talks" to the backend — and to itself

Frontend ↔ backend: exactly one mechanism, everywhere — fetch(url), JavaScript's built-in function for making an HTTP request, returning a Promise (a stand-in for "a value that will exist eventually"), chained with .then(r => r.json()) to parse the response body as JSON, then .then(setSomeState) to store the result. Every component wraps this in its own useEffect + setInterval — polling, not websockets: the browser just asks again on a timer rather than the server pushing updates. This is a deliberate simplicity choice for a prototype — no persistent connection to manage, no reconnect logic, at the cost of up to one polling interval's worth of staleness.

Component ↔ component: in this app, barely at all, on purpose. App.jsx doesn't pass any data down into Dashboard/LPARMonitor/JobHistory/Chat as props — each one independently fetches exactly the data it needs from its own endpoint. That's a real, deliberate tradeoff: no shared data-fetching layer to build or maintain, at the cost of each component repeating similar useEffect/fetch boilerplate. For an app this size, four independent tabs is simpler than the alternative.

LPARMonitor.jsx — reshaping flat rows into a chart

buildChartData() — the one non-trivial function in this component
function buildChartData(rows) {
  const byTs = {}
  for (const r of rows) {
    const ts = r.ts?.slice(11,16) || r.hour || ''   // "HH:MM" out of the full timestamp
    if (!byTs[ts]) byTs[ts] = { ts }
    byTs[ts][r.lpar] = r.peak_mips
  }
  return Object.values(byTs).sort((a,b)=>a.ts.localeCompare(b.ts)).slice(-30)
}

The API returns one row per LPAR per reading — flat data. Recharts (the charting library) wants one object per point in time, with each LPAR as a separate named field on that same object, so it can draw three lines. This function regroups: for every incoming row, use its timestamp as a dict key, creating a fresh entry the first time that timestamp is seen, then set that LPAR's value as one field on it. r.ts?.slice(11,16) — the ?. is optional chaining, meaning "only call .slice() if r.ts actually exists, otherwise just produce undefined instead of crashing." Object.values(byTs) turns the dict back into a plain array Recharts can consume, sorted chronologically and trimmed to the most recent 30 points.

Chat.jsx — the one component that POSTs instead of polling

the send function
const send = async (msg) => {
  const message = msg || input.trim()

  setHistory(newHistory)
  setLoading(true)

  setLoading(false)
}

[...history, {...}] is the spread operator — it copies every existing message into a brand-new array, then adds the new one at the end; React state should never be mutated directly (never history.push(...)), always replaced with a new value via setHistory(...), so React can reliably detect that something changed. The parser and graph builder are completely separate — proof from the code

parser.py never imports neo4j, never writes Cypher, never creates a node or a relationship. Its job ends the moment it returns a plain dict like {"name": "PAYROLL", "calls": [...]}. Only graph.py imports neo4j; only graph.py writes MERGE. That import boundary is the boundary between "extracting facts" and "modeling those facts as a graph."

What the parser's output actually looks like — just data, not a graph

How graph.py translates that, field by field, into real Cypher

one dict → Cypher → a stored graph

Every relationship, with what it represents

the six relationship types
(Program) ──CALLS──▶ (Program)
  PAYROLL calls TAXCALC in its own PROCEDURE DIVISION.
  Built from: programs[i]["calls"]

(Job) ──EXECUTES──▶ (Program)
  PAYJOB's JCL has "EXEC PGM=PAYROLL" — the job runs this program.
  Built from: jobs[i]["programs"], filtered against known parsed programs
  (so JCL utility steps like IEFBR14 never become a phantom Program node)

(Program) ──READS──▶ (Dataset)
  PAYROLL's SELECT/ASSIGN names EMP.MASTER.DATA as an input file.
  Built from: programs[i]["reads"]

(Job) ──TRIGGERS──▶ (Job)
  PAYJOB's JCL comment says "TRIGGERS: BILLJOB".
  Built from: jobs[i]["triggers"]

(Job) ──RUNS_ON──▶ (LPAR)
  PAYJOB's JCL comment says "LPAR: LPAR-1".
  Built from: jobs[i]["lpar"]
A real, honest gap — WRITES is documented but never created

The schema handed to the LLM (and this guide's own file map) mention a sixth relationship, (Program)-[:WRITES]->(Dataset). The parser genuinely extracts a writes list from WRITE/REWRITE statements. But load_relationships() has no loop reading it — only READS is implemented. Not a crash (the LLM would just get an empty result if it ever tried MATCH (p)-[:WRITES]->(d)), but a genuine mismatch between the documented schema and the loader's real behavior — worth knowing cold if asked.

24 smf_store.py, line by line

A SQLite database is one Excel workbook file. A table is one sheet. A row is one record. A column is one field, same for every row.

The setup — lines 1–13

sqlite3 ships with Python itself — nothing to install, and unlike Neo4j or ChromaDB there's no server process at all, just a single file: DB_PATH = .../.maia_smf.db. Delete that file and the database is gone; copy it and you've copied the whole database.

get_conn() — opening the workbook
def get_conn():
    conn = sqlite3.connect(DB_PATH)
    conn.row_factory = sqlite3.Row   # rows become dict-like, not plain tuples

init_db() — declaring the two sheets

Why "with get_conn() as c:" is everywhere

A context manager: open, do the work, clean up automatically — even on error. Specifically for SQLite, exiting the block cleanly auto-commits (saves to disk); an exception inside auto-rolls-back (discards the half-finished change). Skip it and you can write code that looks like it saved data but never actually persisted it.

insert_lpar() / insert_job() — writing one row

the one write pattern used everywhere
now = datetime.now()                         # ask the OS what time it is, once
c.execute("INSERT INTO lpar_performance (...) VALUES (?,?,?,?,?,?,?,?)",
          (lpar, label, now.strftime("%Y-%m-%d"), ...))

INSERT INTO table (cols) VALUES (?,?,...) adds one new row — the SQL equivalent of typing a new line into an Excel sheet. The ? placeholders (never pasting values directly into the SQL text) prevent SQL injection — if a value ever contained something like '); DROP TABLE job_history; --, a plain string-built query would execute that as code; a placeholder always treats it as inert data, no matter its contents. insert_job()'s cpu_secs column isn't a raw input — it's computed right there, int(elapsed_mins * 60 * mips / 100), from the two values that are passed in.

recent_lpar() / recent_jobs() — reading rows back, in the right order

recent_lpar(n=40)
SELECT * FROM lpar_performance ORDER BY ts DESC LIMIT ?
-- SELECT *        "every column"
-- ORDER BY ts DESC  newest timestamp first
-- LIMIT ?          cap the result — without it, every row ever
--                   inserted would come back, potentially tens of
--                   thousands after weeks of the simulator running

The Python side does one more thing worth noticing: reversed(rows) flips newest-first back to oldest-first, because a line chart needs to draw left-to-right chronologically, while the SQL had to fetch newest-first to correctly pick "the most recent 40" in the first place. recent_jobs() is identical but skips the reversal — a table wants newest-on-top, which ORDER BY ts DESC already gives it directly.

job_stats() — the one query doing real arithmetic inside SQL

aggregation functions, explained one at a time
SELECT job,
       COUNT(*)                            AS runs,        -- how many rows matched, period
       ROUND(AVG(elapsed_mins),1)          AS avg_mins,   -- mean, rounded to 1 decimal
       MAX(elapsed_mins)                   AS max_mins,   -- the single slowest run
       SUM(CASE WHEN rc=0 THEN 1 ELSE 0 END) AS ok  -- count rows where rc=0
FROM job_history WHERE job=?           -- filter FIRST, aggregate what's left

CASE WHEN ... THEN ... ELSE ... END is SQL's if/else expression — for each row it evaluates to 1 or 0; wrapping it in SUM(...) then counts how many rows satisfied the condition, expressed as "add up a 1 for every qualifying row." .fetchone() instead of .fetchall() here because this query always collapses down to exactly one summary row, never a list.

chunk 8:  559 chars   ### SOP-003: High LPAR CPU Response

Chunk 4 — the longest, nearly the entire old 2000-char budget by itself — is exactly the one most likely to have been split before. Now a search hit returns it complete: root cause, fix, and Ramesh's note, together, never partial.

The actual code

backend/stores/vector_store.py — ingest_file()
sections = re.split(r"\n(?=### )", text)
chunks = [s.strip() for s in sections if s.strip()]

In plain English: "cut the text apart right before every line starting with ### , but don't consume that heading line — leave it at the start of the next piece." The (?=### ) is a regex lookahead — it checks what follows without including it in the cut, which is exactly why each resulting chunk still starts with its own ### ADR-001: heading rather than losing it. Before adding the fresh chunks, any existing ones tagged source: fname get deleted first (col().delete(where={"source": fname})) — the same idempotency principle the SQLite seeding function was missing (and got fixed for) earlier in this project, so re-running ingestion never silently duplicates the runbook.

Why this matters more than it sounds

This file's entire job is making sure the LLM's search results are complete answers. Get the chunking wrong, and the smartest model can only synthesize from whatever fragment it was handed — if that fragment is half an incident, the answer will confidently omit the other half. This change doesn't make the model smarter; it makes sure it's never shown half a story.

A CPU/R4HA spike, start to finish — including exactly where Gemini gets involved

This is the one trace worth having fully memorized — it's also the exact sequence that exposed bugs #9–12 in Bugs found & fixed, so it doubles as a tour of why the current design looks the way it does.

1

The spike happens — 0 seconds

Either the simulator randomly rolls it (lpar3_spike 8% chance, rha_risk 5% chance, per 10-second cycle), or it's genuine load. insert_lpar() writes one new row into lpar_performance with an elevated cpu_pct/peak_mips. No alert exists yet — this is just a row in a table.

2

The alert engine notices — within 30 seconds, zero LLM

alerts.evaluate_all() runs its plain-SQL rules. rule_lpar_cpu_high() sees cpu_pct > 85; rule_rha_spike() checks whether the rolling average across the whole estate crossed 9,000 MSU. An alert dict is built — {"id": "cpu_high_LPAR-3", "severity": "CRITICAL", ...}. This step is instant and free, by design — see alerts.py, line by line.

3

Published immediately, unconditionally — no waiting on AI

_active_alerts is reassigned right away, before anything AI-related is even considered. This is deliberately the fix for bug #9: your Dashboard's very next poll (≤30s) shows the raw alert card the instant it exists — red/orange, styled by severity — with zero dependency on how fast (or whether) Gemini responds.

4

If it's schedule-shaped, a suggestion is queued in the background

Only alert ids starting with cpu_high_, contention_, or rha_ qualify — job failures and overtime need root-cause investigation, not a retime, so they never trigger this path at all. main.py checks recommendations.get_cached() first; on a brand-new alert there's nothing cached, so a fire-and-forget background task starts. The Dashboard does not wait for it — that's bug #9's fix again, from the other side.

5

The background task gathers real context, then makes exactly one Gemini call

_lpar_context() queries Neo4j for every job on that LPAR plus its schedule and dependencies. _runbook_context() semantically searches ChromaDB using the alert's own text — usually surfacing the exact relevant incident (INCIDENT-003/SOP-003, for a CPU spike). Both get assembled into one prompt; this is the only point in the whole flow where Gemini is involved at all — one call, not a tool-calling loop, capped at a 45-second timeout (bug #12's fix). Full walkthrough: recommendations.py, line by line.

6

The suggestion attaches — usually one cycle later, from cache

If Gemini responds, the text is cached for an hour and attached to the alert. It typically misses this cycle's alert object (the Gemini call takes longer than the 30-second cycle does), so it shows up on the next poll instead — the bare alert card renders first, then the 💡 recommendation appears a beat later, not simultaneously. If Gemini fails or times out instead (quota, rate-limit), the alert just keeps showing with no suggestion, forever — never broken by it.

7

It keeps reappearing, cache-only, until the condition actually clears

Same alert id → the same alert, cycle after cycle — the cached suggestion is reused instantly each time (bug #11's fix: no repeat Gemini calls for a still-active alert). The moment the CPU reading drops back under 85%, or ages out of the 2-minute recency window rule_lpar_cpu_high() checks, evaluate_all() simply stops returning it — nothing has to actively "resolve" it, it just isn't in the next result set.

28 Design decisions worth defending

Four choices that sound arbitrary until you say the "why" out loud.

Why give the model only a schema, never the data?

Token cost becomes a function of the schema's size, not the estate's. Ten programs or ten thousand, the system prompt stays ~300 tokens — the model earns the right to see any particular row by asking for it through a tool call, which is also what makes every answer groundable: if it didn't call a tool, it shouldn't know a specific number.

Why does the alert engine never call an LLM?

Because it can't afford to be probabilistic or slow. Threshold checks need to be deterministic and cheap enough to run every 30 seconds indefinitely — and, as this build's own quota troubleshooting showed, external model APIs are exactly the dependency you don't want sitting between a user and "is anything on fire right now."

Why three separate MCP servers instead of one with three tools?

It mirrors three genuinely separate concerns and ownership boundaries — in a real deployment you could plausibly reach `neo4j_server.py` from more than one client, or replace one store without touching the others' processes. It also matches how MCP is used in practice: a server per system, not a monolith.

Why is there no Layer 4 (automation)?

Real mainframe changes go through Change Approval Boards and multi-week parallel-run validation. An agent that could execute changes on its own would never clear that bar in a real institution — so the system's job stops at producing a recommendation a human reads and acts on.

29 Bugs found & fixed this build

The actual debugging trail — good interview material precisely because none of these were guesses; each was chased down with a concrete reproduction.

1 · tree-sitter-languages has no COBOL, at all

Symptom: parser fell back to regex with an AttributeError. Root cause, proven not assumed: nm on the compiled languages.so showed zero tree_sitter_cobol symbol. Fix: compiled a real grammar from source, pinned the one tree-sitter version that still supports Language.build_library().

2 · The grammar's own AST shape broke the first attempt

Symptom: the walker assumed nested if_statement nodes that don't exist in this grammar. Root cause: found by dumping the real parse tree instead of trusting node-type assumptions — IF/EVALUATE are flat sibling markers. Fix: rewrote conditional-call detection as a depth counter threaded across sibling lists. Bonus: this also fixed a latent bug where the regex parser mis-flagged BILLING's unconditional CUSTMGMT call as conditional.

3 · Neo4j had a phantom 7th program

Symptom: /api/stats reported 7 programs, not 6. Root cause: graph.load_relationships() created a Program node for every EXEC PGM= in JCL, including IEFBR14 — IBM's standard no-op utility, not a real COBOL program. Fix: filter to programs actually present in the parsed COBOL set before creating the relationship.

4 · Ingestion silently duplicated 14 days of history, every run

Symptom: Job History was 100% NIGHTLY, no PAYJOB/BILLJOB visible. Root cause: the idempotency guard checked count > 50, but a single seed pass inserts far fewer rows than that — so it never tripped, and every re-run (which start.sh does on every launch) piled another 14-day block on top. Fix: count > 0.

5 · Anthropic's MCP connector can never reach localhost

Symptom: chat threw unexpected keyword argument 'mcp_servers'. Root cause: that parameter only exists on the beta endpoint — but even fixed, Anthropic's cloud infrastructure has no route to a developer's localhost. Not fixable by any SDK version. Fix: in-process/local MCP client instead of the remote connector.

6 · google-genai's own MCP tool converter crashes on valid schema

Symptom: AttributeError: 'bool' object has no attribute 'items' deep in Google's SDK. Root cause: FastMCP's generated schemas set additionalProperties: false (a bool) — the SDK's schema filter assumed every field under that key was a nested dict. Fix: switching to langchain-mcp-adapters' own converter sidestepped it entirely.

7 · Gemini's free quota is per-model, not per-account

Symptom: 429s that switching libraries (raw SDK → LangChain) obviously couldn't fix — a misconception worth naming plainly: LangChain has no quota of its own; it calls the same API with the same key. Root cause: gemini-flash-latest resolved to a model with a 20-requests/day cap on this key, while gemini-2.0-flash had zero free entitlement at all (deprecated). Fix: tested models directly to find one with an actually-usable, separate quota bucket (gemini-flash-lite-latest).

8 · A model's reply shape isn't guaranteed to be a plain string

Symptom: would have leaked raw [{'type': 'text', ...}] block dicts into the chat UI. Root cause: some models (this one has thinking=True) return .content as a list of content blocks, not a string. Fix: AIMessage.text, LangChain's normalized accessor, instead of reading .content directly.

9 · Publishing alerts was accidentally coupled to LLM latency

Symptom: after adding AI reschedule suggestions, the Dashboard stopped showing any alerts at all, even ones confirmed to exist by querying the rule directly. Root cause: alert_loop() was written to await the Gemini suggestion call before reassigning _active_alerts — since a suggestion call can take 40–90+ seconds, the entire alert list stayed frozen at its previous (stale/empty) value for that whole time, directly violating the project's own "alerts must stay available even if the LLM is slow" principle. Fix: publish _active_alerts immediately, unconditionally, every cycle; generate suggestions as fire-and-forget asyncio.create_task() background tasks that mutate the alert dict in place once ready, never blocking the publish step.

10 · A timezone mismatch had silently broken every alert's recency window, project-wide

Symptom: while debugging #9, an alert appeared with a timestamp from over an hour in the past yet still passed a "last 2 minutes" filter. Root cause: smf_store.py stamped every row using datetime.now() — local wall-clock time — while every alerts.py rule compares against SQLite's own datetime('now', '-N minutes'), which is always UTC. On a system several hours ahead of UTC, locally-stamped rows looked perpetually "in the future" relative to that UTC cutoff, meaning every recency window in the alert engine had been silently wrong for the project's entire history — not a regression from this specific feature, just newly discovered while building it. Fix: compute ts from datetime.now(timezone.utc), formatted to match SQLite's own datetime('now') output exactly (space separator, no 'T', no offset suffix) — then cleared and reseeded the contaminated historical rows, since old locally-stamped data would otherwise keep looking falsely "recent" forever.

11 · An alert that stayed active across cycles spawned a new concurrent Gemini call every 30s

Symptom: after fixing #9, a live test still hung with no suggestion appearing for 90+ seconds. Root cause: the same still-uncached alert id was re-evaluated every 30-second cycle, and each cycle spawned a brand-new background task for it rather than waiting for the first one to resolve — several redundant, concurrent Gemini calls piling up against an already-tight free-tier quota. Fix: an in-flight set() of alert ids currently being generated, checked before spawning a new task, cleared in a finally block when the task completes.

12 · No timeout meant a stalled call could block that alert's retries forever

Symptom: a direct diagnostic call, wrapped in an explicit asyncio.wait_for(..., timeout=60), genuinely timed out with no response at all — different from the instant 429 errors seen earlier in this session, and most likely heavy throttling from cumulative testing. Root cause: nothing in suggest_reschedule() bounded how long the Gemini call could take — a hung request would leave that alert's entry in fix #11's in-flight set stuck forever, permanently preventing any future retry for it, even after conditions improved. Fix: asyncio.wait_for(llm.ainvoke(...), timeout=45) inside suggest_reschedule() itself, so a stalled call fails cleanly instead of hanging, letting the finally block from fix #11 release the in-flight guard and permit a future attempt.

30 Talking points for the interview

Likely questions, and the shape of a strong answer — not a script to recite.

"Walk me through the architecture."

Start from the two request paths, not the file list: a zero-LLM polling path for live monitoring (simulator → SQLite/Neo4j → alert rules → REST → React polling), and a single LLM path for open-ended Q&A (schema context → LangChain → MCP tool calls → real stores → grounded answer). Naming that split first shows you understand why the system is shaped the way it is, not just what's in each file.

"What's the hardest bug you hit, and how did you find it?"

The COBOL grammar work is the strongest story: proved the "no COBOL grammar" problem with nm on a compiled binary rather than guessing from an error message, compiled a real grammar from source, then discovered the AST's actual shape by dumping real parse trees instead of trusting assumed node names — and that discovery directly fixed a second, previously-invisible bug in the regex parser it was replacing.

"Why MCP instead of just calling Python functions directly?"

MCP standardizes the boundary between "a model that wants to act" and "a system that can act on its behalf" independent of vendor — the same 3 servers could serve Gemini, Claude, or any other MCP-speaking client without changing a line of server code. This project actually exercised that: swapping the model twice (Claude→Gemini, raw SDK→LangChain) never required touching mcp_servers/ at all.

"What would you build next?"

Proactive scheduling advice on the Dashboard (see recommendations.py) is now built — but only for the 3 alert types that are inherently timing questions. Still on the roadmap: a full Recommendations tab with the other specialist agents from the original design (cost, modernisation, operational-pattern scanning, not just scheduling), an Impact Analysis tab surfacing the actual Cypher the model wrote for transparency, and a real z/OSMF connector to replace the simulator — the architecture was explicitly built so Layer 1 upward never needs to know where the data came from.

"Why FastAPI instead of Flask?"

Two concrete reasons this project actually needs: native async def support (Flask's is bolted-on and clunkier), which matters directly because the chat endpoint and the background alert/simulator loops are all async; and automatic request validation via Pydantic (ChatRequest) plus free interactive docs at /docs, both generated from the same type-annotated code rather than hand-maintained separately.

"Why Neo4j instead of plain SQL for the dependency graph?"

The signature query this app needs — "what's impacted, however many hops away" — is a variable-length traversal (*1..6). In SQL that's a recursive CTE per relationship type, multiplied across CALLS/EXECUTES/TRIGGERS; in Cypher it's one line. When the question is fundamentally about relationships, not rows, a graph database stops fighting the shape of the data.

"Why ChromaDB instead of just full-text search in SQLite?"

Because "why does BILLJOB keep failing" needs to match an incident report that never uses the word "fail" — it says "RC=8" and "dataset contention." Full-text search matches keywords; embeddings match meaning, which is the only way prose written by a different person, in different words, about the same underlying fact gets found at all.

"Why is ingestion a separate file from the things that query the data?"

Ingestion runs once (or on-demand); querying happens on every chat turn and every 10-second simulator tick. Mixing them would mean every query-time file also carries parsing/loading code it never calls in the hot path — and, concretely in this project, the parser and graph-loading logic changed independently of each other multiple times (the IEFBR14 fix, the AST rewrite) without the querying code ever needing to change at all.

"Why background tasks instead of a separate cron job or process?"

asyncio.create_task() inside the same FastAPI process means the simulator, alert loop, and HTTP server all share one Python runtime and one event loop — no separate process to deploy, monitor, or restart independently, and no IPC needed to get simulator-generated data into the same SQLite file the API reads from. For a single-instance prototype, that simplicity outweighs the isolation a separate process would buy.

"How does scheduler_ai (recommendations.py) avoid hallucinating a bad suggestion?"

Two layers: retrieval before generation — it fetches the real job schedule from Neo4j and the real incident text from ChromaDB before ever calling Gemini, so there's real material to ground an answer in — and an explicitly-engineered prompt (see the full walkthrough) that tells the model to defer to the runbook's own prescribed fix, to check a job's dependencies before suggesting a new time, and to say "no change needed" rather than force an answer. Two of those three rules exist because the first version of this feature got them wrong in testing.

"Why retrieve from both Neo4j and ChromaDB before calling the LLM, instead of just one?"

They answer different halves of the same question. Neo4j has the structural facts (which job, what schedule, what depends on what) — ChromaDB has the narrative facts (why this specific failure happens, what fixed it last time). A recommendation grounded in only the schedule might suggest a technically-valid time that ignores known history; grounded in only the runbook, it might not know a job's real dependencies. Combining both before the single Gemini call is what lets the model's one answer cite both a specific time and a specific precedent.

"Why keep the regex parser as a fallback instead of requiring the tree-sitter grammar?"

Building the grammar requires cloning a repo and running a C compiler — a real dependency that might not be available in every environment (CI, a fresh clone, a locked-down machine). Regex at 80% accuracy that always works beats an AST parser at 95% accuracy that sometimes can't even start.

"Why dataclasses for COBOLProgram/JCLJob instead of plain dicts?"

Type hints catch a typo'd field name at review time instead of silently returning None at runtime; field(default_factory=list) sidesteps Python's shared-mutable-default trap that a hand-rolled dict-based version would need to remember to avoid on every single list field. .to_dict() is then the one deliberate seam where the type safety is traded away, right at the boundary where a plain dict is actually needed (JSON, the Neo4j driver).

"Why simulate data instead of hardcoding some fixed rows?"

Fixed rows would make every chart flat and every "recent" query eventually run dry as their timestamps aged out of any real time window. A simulator that keeps generating plausible new data, continuously, on a realistic hourly rhythm plus occasional anomalies, is what makes alerts, charts, and chat answers stay meaningful no matter how long the demo has been running.

"How would the simulator be replaced in a real deployment?"

simulator.py is the only file that would change — it would be swapped for real z/OSMF API calls (jobs, datasets) and real SMF/RMF record ingestion, both writing into the exact same insert_lpar()/insert_job() functions in smf_store.py. Nothing above that layer — the alert rules, the chat tool loop, the React frontend — would need to know the difference, which is exactly the point of keeping data generation and data storage in separate files.
